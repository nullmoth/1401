# 01 WhateverXe 集成现状审计

## 1. 审计目标与方法

本报告回答三个问题：

1. 1401 的 Windows EFI Builder 是否真的为 `8086:A7A0` 选中并配置了 WhateverXe，而不只是 Mac App 里有一个
   “Intel Xe graphics”开关？
2. 生成出来的 EFI 是否满足 b00t0x WhateverXe 0.8.0 / WhateverXe Graphics v0.4.1 的启动前置条件？
3. 如果满足，是否等同于“已经具备图形加速能力”？

方法：静态跟踪 Windows 构建器从硬件扫描到 `config.plist` 的完整调用链；对真实 MateBook 扫描（
`out/huawei-scan/Report.json`）重新构建独立 EFI；用 `scripts/verify_efi.py`、`ocvalidate`、单元测试和 Mac
setup 脚本测试验证；只把官方 README/设备表当作“上游文档”证据，不把 README 当成实机结果。

## 2. Windows EFI Builder 的实际调用链

### 2.1 硬件扫描

`out/huawei-scan/Report.json` 中：

- `GPU["Intel(R) Iris(R) Xe Graphics"]`：`Manufacturer = Intel`、`Device ID = 8086-A7A0`、
  `Device Type = Integrated GPU`、`Codename = Raptor Lake-P`、`PCI Path = PciRoot(0x0)/Pci(0x2,0x0)`。
- `Monitor["CSO1415"]`：`Connector Type = Internal`、`Resolution = 3120x2080`、连接在该 Intel GPU 上。

这是后续规则能命中的前提：上游的 WhateverXe 分支要求 `Device Type` 含 `Integrated GPU`，并从 `Device ID`
取第 5 位之后的 4 位十六进制。

### 2.2 引擎加载与上游选择

- `p1401/engine.py:407-419`：`_load_engine()` 把 `upstream/OpCore-Simplify` 加入 `sys.path`，加载
  `OpCore-Simplify.py`，并在构建前调用 `whateverxe.pin_downloads()`（本次新增）固定 WEX/AMFIPass Mod 版本。
- `upstream/OpCore-Simplify/Scripts/datasets/gpu_data.py:75-82`：`WhateverXeDeviceIDs` 是 Tiger Lake、
  Alder Lake-P/N/S、Twin Lake、Raptor Lake-P/U/S 的并集；A7A0 在其中。
- `upstream/OpCore-Simplify/Scripts/kext_maestro.py:415-432`：遍历 GPU，若 `Device Type` 含
  `Integrated GPU`、厂商是 Intel、`Device ID[5:]` 在 `WhateverXeDeviceIDs` 中，则打印
  “WhateverXe is experimental”，追加 `WhateverXe`，并 `break`（同一时间只选一个 GPU 驱动）。
- `upstream/OpCore-Simplify/Scripts/compatibility_checker.py:128-130`：对 WhateverXe ID 把最低 macOS
  版本设为 `20.0.0`，避免上游把 Xe-LP 判成“无驱动”而退出。
- `upstream/OpCore-Simplify/Scripts/config_prodigy.py:370-376`：当 `WhateverXe` 被选中时，向该 iGPU 的
  `DeviceProperties` 写入 `framebuffer-patch-enable=01000000` 与 `framebuffer-stolenmem=0000C003`
  （60 MB DVMT 方案）。
- `upstream/OpCore-Simplify/Scripts/config_prodigy.py:660-662`：追加 boot-args
  `-allow3d -disablegfxfirmware -igfxdvmt`。
- `upstream/OpCore-Simplify/Scripts/gathering_files.py:215-216`：当 `AMFIPass` 与 `WhateverXe` 同时被选中时，
  把下载产品名改成 `AMFIPass-b00t0x`；`gathering_files.py:82-83` 把
  `kext_data.AMFIPassModDownloadInfo` 放进 `latest_products`。因此 Windows 构建器实际下载的是作者修改版
  AMFIPass，而不是上游 AMFIPass。

### 2.3 真实构建的日志证据

`reports/logs/huawei-build-release.log:61` 的构建上下文包含：

```text
*** Found Intel(R) Iris(R) Xe Graphics is Intel Raptor Lake-P GPU.
Important: WhateverXe is experimental.
Apply the Xe root patch from https://github.com/b00t0x/WhateverXe-Graphics
AMFIPass Mod will be used.
```

同一构建的 `out/huawei-efi-release/EFI/OC/config.plist` 中，`Kernel/Add` 为 30 项，包含：

| 条目 | 位置 | Enabled | MinKernel |
|---|---|---:|---|
| `Lilu.kext` | 0 | true | 空 |
| `AMFIPass.kext` | 1 | true | `20.0.0` |
| `WhateverXe.kext` | 27 | true | `20.0.0` |
| `WhateverGreen.kext` | 不存在 | — | — |

`reports/hardware/efi-file-check-release.json:161,256` 也分别验证了“kext entry resolves WhateverXe.kext”和
“Huawei-relevant kext WhateverXe.kext present”。

**结论 1：Windows EFI Builder 确实覆盖了 WhateverXe 的 kext 选择与注入阶段；这不是 Mac App 独有的功能。**
但 kext 注入只是图形加速链的第一步，见第 7、8 节。

## 3. 8086:A7A0 的识别证据

### 3.1 1401 自己的分类表

`p1401/intel_gpu.py:29-35` 的 `WHATEVERXE_IDS` 有 60 个 ID，包含 `A7A0`；`p1401/intel_gpu.py:46` 把
`A720 A721 A7A0 A7A1 A7A8 A7A9 A7AA A7AB A7AC A7AD` 归入 `Raptor Lake-P (Xe-LP)`。

`tests/test_intel_gpu.py` 会检查：

- `WHATEVERXE_IDS` 中每个 ID 都能被 `classify()` 归入一个 family；
- `p1401/intel_gpu.py` 的 ID 列表、`mac/Sources/main.swift` 的 `App.xeIds`、
  `mac/Resources/nullmoth-setup.sh` 的 case 列表三者完全一致。

### 3.2 上游设备表

`upstream/OpCore-Simplify/Scripts/datasets/gpu_data.py:75-82` 的 `WhateverXeDeviceIDs` 与
`p1401/intel_gpu.py:WHATEVERXE_IDS` 都是 60 项；本次审计用脚本比较，差集为空：

```text
len(WHATEVERXE_IDS) = 60
len(WhateverXeDeviceIDs) = 60
set difference (both directions) = empty
```

### 3.3 官方设备表

<https://github.com/b00t0x/WhateverXe/blob/0.8.0/docs/device-selection.md> 把 `A7A0` 列在
“Raptor Lake-H / P”下：`A720`, `A7A0`, `A7A8`, `A7AA`, `A7AB`。同一页明确写：

> “An implemented backend does not imply hardware validation for every ID or connector.”

**结论 2：A7A0 在 1401、OpCore 和上游官方设备表中都被识别为 WhateverXe 目标；识别层面没有缺口。**

## 5. Lilu / WhateverXe / AMFIPass 的依赖与顺序

官方 README 0.8.0 的安装步骤：

1. Add Lilu, `WhateverXe.kext` and AMFIPass 1.4.1 Mod to OpenCore, with WEX after Lilu.
2. Set `csr-active-config=03080000` (0x803) and apply the configuration.
3. Boot macOS, install WhateverXe Graphics, restart.

候选 EFI 的实际顺序（`config.plist: Kernel/Add`）：

```text
0  Lilu.kext            Enabled
1  AMFIPass.kext        Enabled
...
27 WhateverXe.kext      Enabled  MinKernel 25.7.0
```

验证脚本 `scripts/verify_efi.py:79-108` 检查：

- WEX 已启用；
- Tahoe 的 WEX `MinKernel == 25.7.0`；
- 在启用列表里 Lilu 的索引小于 WEX；
- AMFIPass 已启用；
- WhateverGreen 不存在或未启用；
- `-allow3d`、`-disablegfxfirmware` 都在 boot-args；
- `csr-active-config` 包含 `0x803`；
- WEX bundle 版本为 0.8.0。

候选 EFI 的 82 项检查全部通过，`ocvalidate` 0 问题。

## 6. `csr-active-config`：发布 EFI 的真实缺陷

### 6.1 已发布示例 EFI 的值

`out/huawei-efi-release/EFI/OC/config.plist` 中：

```text
csr-active-config = 03 00 00 00  (0x00000003)
```

`reports/logs/huawei-build-release.log:9171-9174` 记录了原因：

```json
{
  "rule": "sip-minimal",
  "before": "030a0000",
  "after": "03000000",
  "why": "VoodooHDA on Tahoe loads from /Library/Extensions (Dortania: csr 03000000)"
}
```

但同一构建的 `decisions` 中，音频菜单实际选择的是 `2`（AppleALC + SimpleHDA），EFI 里并没有
`VoodooHDA.kext`。旧规则只凭 `Select audio kext` 这个 prompt 和默认策略 `tahoe_audio="voodoohda"` 就认定
“有 VoodooHDA”，把 SIP 从引擎默认的 `0x0A03` 降到了 `0x03`。

### 6.2 为什么这会让 WhateverXe 失败

官方 WhateverXe README 0.8.0 的 Installation 第 2 步：

> Set `csr-active-config=03080000` (`0x803`) and apply the configuration.

WhateverXe Graphics v0.4.1 README 的 Requirements：

> SIP setting `csr-active-config=03080000` (`0x803`). Full SIP is unsupported.

`0x03` 只有 `CSR_ALLOW_UNTRUSTED_KEXTS | CSR_ALLOW_UNRESTRICTED_FS`，没有 `0x800`
（`CSR_ALLOW_UNAUTHENTICATED_ROOT`）。WhateverXe Graphics 安装到 `/Library` 并重建 AuxKC；官方要求
`0x803`。因此：

- EFI 能启动 WEX kext（OpenCore 注入不受 SIP 这一位影响），但 macOS 内的 WhateverXe Graphics 安装/重建
  AuxKC 缺少官方要求的前置位；
- 也就是说，**发布版 Windows 构建器生成的 EFI 不是官方意义上的“WhateverXe-ready EFI”**。

发布标签本身也带着这段逻辑：`git show v2.9.1-huawei.1:p1401/policy.py` 的第 660-661 行仍是
`policy.tahoe_audio == "voodoohda"` + prompt 判断；`git show v2.9.1-huawei.1:mac/Resources/nullmoth-setup.sh`
的第二次运行分支仍是“WEX 已加载 → 直接装 Graphics”。所以这不是只在 `main` 上出现的后续问题。

### 6.3 本次修复

用本次新增的 WEX 检查直接跑 2.9.1 示例 EFI，结果只有两项失败：

```text
WhateverXe Tahoe MinKernel is 25.7.0: 20.0.0
WhateverXe SIP includes 0x803: 0x0003
```

完整结果：`reports/hardware/efi-file-check-release-whateverxe.json`。这从文件级证明发布示例 EFI 的 WEX
前置条件不完整；候选 EFI 的同一组检查 82/82 通过。

`p1401/policy.py:687-719`：

- `voodoo` 改为真正的 `"VoodooHDA.kext" in enabled`，不再从菜单 prompt 推断；
- 当 WEX 启用时，SIP 目标为 `cur | 0x803`，保留 OCLP/NVIDIA 等其他功能已有的位；
- 如果前面的 `sip-minimal` 仍然把值降到了不含 `0x803`，后面的 `whateverxe-sip` 再兜底抬升。

候选 EFI 的实际值是 `0x00000A03`：`0x0A03 = 0x800 | 0x200 | 0x003`，包含 `0x803` 的全部位，同时保留引擎
默认的 `0x200`（unapproved kexts）。这与 Mac App 的 `cur | 0x803` 语义一致；官方正常安装写的是 `0x803`，
AutoPkg 路径写的是 `0xA03`。本次没有实机验证安装器是“位掩码检查”还是“精确等于”；见风险清单。

`tests/test_whateverxe_integration.py` 覆盖：

- WEX + `csr=0x03` → 最终含 `0x803`；
- WEX + `csr=0x0A43` → 保留 `0x0A43`；
- 没有 VoodooHDA kext 时，音频菜单 prompt 不再降低 SIP；
- 真正的 `VoodooHDA.kext` 启用时仍降到 `0x03`；
- WEX 与 WhateverGreen 同时存在时关闭 WhateverGreen；
- WEX 缺少 boot-args 时补齐；
- Tahoe 构建把 WEX `MinKernel` 设为 `25.7.0`，Sequoia 构建不动。

## 7. 版本与安装流程：Windows 端做了什么、没做什么

### 7.1 Windows 端

- 通过 OpCore Simplify 选择并下载 `WhateverXe.kext`。
- 通过 `AMFIPass-b00t0x` 产品名下载作者修改版 AMFIPass。
- 写入 WEX 所需的 DeviceProperties 和 boot-args。
- 把 WEX 放进 `Kernel/Add`，并放入 `EFI/OC/Kexts/WhateverXe.kext`。

### 7.2 Windows 端不做的事

- **不安装 WhateverXe Graphics**。该包是 macOS installer package，安装到运行中 macOS 的 `/Library` 并重建
  AuxKC；Windows 构建器无法执行。
- **不固定 WhateverXe 版本**（修复前）。上游 `gathering_files.py` 对没有 `download_info` 的 kext 调用
  `github.get_latest_release()`，所以“今天构建”拿到的是当天最新 release。2.9.1 构建时最新是 0.8.0，但这
  不是可复现的固定版本。
- **不固定 AMFIPass Mod 的 commit**（修复前）。上游 `AMFIPassModDownloadInfo` 指向
  `refs/heads/main/extras/...`，不是固定 commit。

### 7.3 修复后的版本固定

新增 `p1401/whateverxe.py`：

| 项目 | 固定值 |
|---|---|
| WhateverXe | `0.8.0`，`WhateverXe-0.8.0-RELEASE.zip`，SHA-256 `5b71e14c…`，大小 2,099,802 |
| AMFIPass Mod | `AMFIPass-v1.4.1-Mod-RELEASE.zip`，commit `88d64a3…`，SHA-256 `71f41de4…`，大小 185,766 |
| WhateverXe Graphics | `v0.4.1`，`WhateverXe-Graphics-0.4.1.pkg`，SHA-256 `7f7ce3b9…`，大小 95,200,578 |

`p1401/engine.py:417-418` 在引擎加载后调用 `whateverxe.pin_downloads()`，把 WEX 的
`download_info` 和 `AMFIPassModDownloadInfo` 替换成上述固定值。OpCore 的下载器会校验 `sha256`；候选构建
日志中可以看到：

```text
Updating WhateverXe...
from https://github.com/b00t0x/WhateverXe/releases/download/0.8.0/WhateverXe-0.8.0-RELEASE.zip
Verifying SHA256 checksum...
Checksum verified successfully.
Updating AMFIPass-b00t0x...
from https://github.com/b00t0x/WhateverXe-Graphics/raw/88d64a.../extras/AMFIPass-v1.4.1-Mod-RELEASE.zip
Verifying SHA256 checksum...
Checksum verified successfully.
```

`tests/test_whateverxe_integration.py` 还会解析 `mac/Resources/nullmoth-setup.sh` 中的 WEX/AMFIPass/Graphics
pin，要求 Windows 端常量与 Mac App 完全一致；两者任一漂移都会失败。

### 7.4 Mac App 的第二步

`mac/Resources/nullmoth-setup.sh:1371-1432` 的 `--xe on`：

1. 检查 Intel CPU、iGPU 设备 ID、macOS 版本（15.8.x 或 26.7+）、没有 `-nmxintel`；
2. 如果 `kmutil showloaded` 已看到 `org.b00t0x.WhateverXe`，进入第二步，安装
   `WhateverXe-Graphics-0.4.1.pkg`；
3. 否则把 WEX 加到 Lilu 之后、换上 AMFIPass Mod、关闭 WhateverGreen、补 boot-args、把 SIP 抬到至少
   `0x803`，记录状态并要求重启；
4. 下一次运行再安装 Graphics。

本次还修复了第二步的一个跨构建器缺陷：Windows 生成的 EFI **已经带有 WEX**，所以 Mac App 第一次运行就可能
直接进入“WEX 已加载”分支；旧脚本会在 SIP 仍为 `0x03` 时直接跑 Graphics 安装器。现在
`mac/Resources/nullmoth-setup.sh:1407-1425` 会先检查 `csr_of`，若不含 `0x803` 就先改配置、记录
`CSR_OLD/CSR_NEW`、要求重启，再在下一轮安装 Graphics。`mac/tools/test_xe_whateverxe.py` 新增了三个用例覆盖
“先抬 SIP 不安装”“重启后再安装”“已是 0x803 直接安装”。

### 7.5 Windows 发布包是否带 Mac App

带。`out/release-artifact/1401-Windows-2.9.1.zip` 里包含：

```text
1401/NullMoth/1401-Mac-2.9.zip
1401/NullMoth/nullmoth-nvidia-2.9.tar.gz
```

`1401-Mac-2.9.zip` 里是 `1401.app`，其 `Contents/Resources/nullmoth-setup.sh` 就是执行 `--xe` 的脚本。所以从
Windows 出发的端到端路径是：

```text
Windows 构建器 -> EFI（含 WhateverXe kext + 前置配置）
             -> U 盘上的 1401.app
             -> macOS 启动后运行 1401.app 的 Intel Xe 开关
             -> 第二次运行安装 WhateverXe Graphics
             -> 重启后才有加速
```

这条路径存在，但它**不等于**“Windows EFI Builder 已经完成图形加速集成”：EFI 只是第一步；加速 payload 是
macOS 内的第二次安装。发布包里的 Mac App 是 2.9 版本，仍带 7.4 描述的旧第二步逻辑；候选 EFI 的 SIP 已含
`0x803`，所以旧 Mac App 的第二次运行会直接安装 Graphics，不会被旧逻辑卡住。若用户使用旧 2.9.1 EFI
（SIP=0x03），旧 Mac App 就会命中那个缺陷。

## 8. 生成 EFI 时是否遗漏、覆盖或错误禁用 WEX

逐项检查构建后处理：

| 检查 | 结果 | 证据 |
|---|---|---|
| 后续 pass 是否移除 WEX | 否 | `policy.py` 的 `EXCLUDED_KEXTS` 不含 WEX；`community.apply_efi_drivers` 只加驱动 |
| 后续 pass 是否关闭 WEX | 否 | `bootfix`/`nullmoth` 只处理 NVIDIA/停止日志；候选 EFI WEX Enabled=true |
| 后续 pass 是否覆盖 `csr-active-config` | 修复前会（`0x03`）；修复后不会低于 `0x803` | `policy.py:687-719`；候选 `0x0A03` |
| 后续 pass 是否覆盖 boot-args | 保留并补齐 WEX 必需项 | 候选 boot-args 含 `-allow3d -disablegfxfirmware` |
| 后续 pass 是否重新启用 WhateverGreen | 否 | 候选 EFI 无 WhateverGreen |
| ACPI 是否缺 PNLF | 否 | 候选 `ACPI/Add` 有 `SSDT-PNLF.aml`；`verify_efi.py` 检查 |
| 是否伪造 `device-id`/`ig-platform-id` | 否 | `DeviceProperties` 只有 framebuffer 两项；WEX 官方说通常不需要 |
| 是否加入 `-yTileDisable` | 否 | boot-args 无该项；官方明确不要用 |
| 是否把 WEX 放在 Lilu 之前 | 否 | 索引 0 vs 27 |

## 11. 本报告不能证明什么

- 不能证明候选 EFI 能在本机启动；
- 不能证明 macOS 能安装、进入桌面；
- 不能证明 WhateverXe kext 能加载、Metal/OpenGL/视频解码能工作；
- 不能证明 A7A0 的内部 eDP 3120×2080@90 Hz、亮度、睡眠唤醒能工作；
- 不能证明 WhateverXe Graphics 安装器在本机一定成功。

这些事项全部列在 `04-风险与未验证.md`。本报告只把“代码路径、EFI 文件内容、上游文档、自动化测试”作为
结论依据。
